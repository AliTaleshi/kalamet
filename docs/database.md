# Database design

Kalamet's schema has 17 tables in 5 layers. Each layer depends only on the ones above it, and
each maps to one Flyway migration in `backend/src/main/resources/db/migration` (plus later
additions such as V6) and one Java package. The migrations are the source of truth; this
document explains them.

| Layer | Migration | Tables | Package |
| --- | --- | --- | --- |
| 1. Identity | `V1__identity.sql`, `V6__refresh_tokens.sql` | users, otp_codes, provinces, addresses, refresh_tokens | `user` |
| 2. Catalog | `V2__catalog.sql` | categories, brands, products, product_specs, product_variants, product_images | `catalog` |
| 3. Shopping cart | `V3__cart.sql` | carts, cart_items | `cart` |
| 4. Orders and payments | `V4__orders.sql` | orders, order_items, payments | `order` |
| 5. Engagement | `V5__engagement.sql` | reviews | `review` |

Conventions used everywhere: money is whole Rials (`BIGINT`, Java `long`) and shown as Toman
(Rial / 10); timestamps are `TIMESTAMPTZ` in UTC (Java `Instant`) and shown in the Jalali calendar;
enums are `VARCHAR` with a `CHECK` constraint (`@Enumerated(EnumType.STRING)`); ids are
`BIGINT GENERATED BY DEFAULT AS IDENTITY`.

`otp_codes` has no foreign keys on purpose: a code can be requested for a number that has no
account yet. The user row is created on the first successful verification.

## Layer 1: Identity

```mermaid
erDiagram
  USERS ||--o{ ADDRESSES : has
  PROVINCES ||--o{ ADDRESSES : locates
  USERS ||--o{ REFRESH_TOKENS : signs_in_with
  USERS {
    bigint id PK
    varchar mobile UK "09xxxxxxxxx"
    varchar email UK "optional"
    varchar first_name "filled after first login"
    varchar last_name
    varchar role "CUSTOMER or ADMIN"
    boolean active
  }
  OTP_CODES {
    bigint id PK
    varchar mobile
    varchar code_hash "HMAC-SHA256"
    timestamptz expires_at
    int attempts
    timestamptz consumed_at
  }
  PROVINCES {
    smallint id PK
    varchar name UK
  }
  ADDRESSES {
    bigint id PK
    bigint user_id FK
    varchar recipient_name
    varchar recipient_mobile
    smallint province_id FK
    varchar city
    text address_line
    varchar plaque
    varchar unit
    varchar postal_code "10 digits"
    boolean is_default
  }
  REFRESH_TOKENS {
    bigint id PK
    bigint user_id FK
    varchar token_hash UK "SHA-256"
    timestamptz expires_at
    timestamptz revoked_at
  }
```

- Login is mobile number plus a one-time SMS code; there are no passwords. Only an HMAC of each
  code is stored (keyed with a server secret, because a six-digit code is trivial to recover from
  a plain hash), with an expiry and an attempt counter to stop brute-forcing.
- Access tokens are 15-minute JWTs and are not stored. Refresh tokens (30 days) are random strings
  stored as SHA-256 hashes. Every refresh revokes the used token and issues a new one; presenting
  a revoked token again revokes all of that user's tokens (V6).
- A partial unique index allows at most one default address per user.
- Orders copy the address as text at checkout, so addresses can be edited or deleted freely.

## Layer 2: Catalog

```mermaid
erDiagram
  CATEGORIES ||--o{ CATEGORIES : parent_of
  CATEGORIES ||--o{ PRODUCTS : contains
  BRANDS |o--o{ PRODUCTS : makes
  PRODUCTS ||--o{ PRODUCT_SPECS : describes
  PRODUCTS ||--|{ PRODUCT_VARIANTS : sold_as
  PRODUCTS ||--o{ PRODUCT_IMAGES : shows
  PRODUCT_VARIANTS |o--o{ PRODUCT_IMAGES : pictured_in
  CATEGORIES {
    bigint id PK
    bigint parent_id FK
    varchar name "Persian"
    varchar slug UK "Latin"
    varchar image_url
    int sort_order
  }
  BRANDS {
    bigint id PK
    varchar name
    varchar name_en
    varchar slug UK
    varchar logo_url
  }
  PRODUCTS {
    bigint id PK
    bigint category_id FK
    bigint brand_id FK
    varchar name "Persian title"
    varchar name_en "Latin subtitle"
    varchar slug UK
    text description
    boolean active
  }
  PRODUCT_SPECS {
    bigint id PK
    bigint product_id FK
    varchar group_name
    varchar name
    varchar value
    int sort_order
  }
  PRODUCT_VARIANTS {
    bigint id PK
    bigint product_id FK
    varchar sku UK
    jsonb attributes "e.g. color, size"
    bigint price "Rial"
    bigint compare_at_price "crossed-out price"
    timestamptz discount_ends_at "offer countdown"
    int stock_quantity
    boolean active
    bigint version "optimistic lock"
  }
  PRODUCT_IMAGES {
    bigint id PK
    bigint product_id FK
    bigint variant_id FK "optional"
    varchar url
    varchar alt_text
    int sort_order
  }
```

- A product is the shared description; a variant is what is actually sold. A product without
  options has one variant with `attributes = {}`. Attribute keys are English, values Persian.
- The database rejects a `compare_at_price` that is not higher than `price`, and a
  `discount_ends_at` without a `compare_at_price`.
- Pricing rule: while `discount_ends_at` is in the future (or null), the customer pays `price` and
  sees `compare_at_price` crossed out. Once `discount_ends_at` has passed, the offer is over and the
  customer pays `compare_at_price`, the regular price. `PriceQuote` implements this in Java and
  `ProductSearch` repeats it in SQL.
- `version` makes concurrent stock updates safe: when two checkouts race for the last unit, one
  gets an optimistic-lock conflict (HTTP 409) instead of overselling.
- Products and variants are never hard-deleted once sold (order items reference variants); set
  `active = false` instead.

## Layer 3: Shopping cart

```mermaid
erDiagram
  USERS ||--o| CARTS : owns
  CARTS ||--o{ CART_ITEMS : holds
  PRODUCT_VARIANTS ||--o{ CART_ITEMS : added_as
  CARTS {
    bigint id PK
    bigint user_id FK, UK
  }
  CART_ITEMS {
    bigint id PK
    bigint cart_id FK
    bigint variant_id FK
    int quantity
    timestamptz added_at
  }
```

- One persistent cart per user (`UNIQUE user_id`), created lazily on first add-to-cart.
- `UNIQUE (cart_id, variant_id)`: adding the same variant again increases the quantity.
- Cart items store no price, so the cart always shows current prices. Stock is checked on add
  and again at checkout, where it is decremented.

## Layer 4: Orders and payments

```mermaid
erDiagram
  USERS ||--o{ ORDERS : places
  ORDERS ||--|{ ORDER_ITEMS : contains
  PRODUCT_VARIANTS ||--o{ ORDER_ITEMS : bought_as
  ORDERS ||--o{ PAYMENTS : paid_by
  ORDERS {
    bigint id PK
    bigint user_id FK
    varchar order_number UK
    varchar status
    bigint items_total
    bigint discount_total
    bigint shipping_fee
    bigint total "items_total + shipping_fee"
    varchar ship_recipient_name "address snapshot"
    varchar ship_province
    varchar ship_city
    varchar ship_postal_code
  }
  ORDER_ITEMS {
    bigint id PK
    bigint order_id FK
    bigint variant_id FK
    varchar product_name "snapshot"
    varchar sku "snapshot"
    jsonb variant_attributes "snapshot"
    bigint unit_price
    bigint original_price
    int quantity
    bigint line_total
  }
  PAYMENTS {
    bigint id PK
    bigint order_id FK
    varchar gateway "ZARINPAL or MOCK"
    varchar authority UK
    varchar ref_id UK
    varchar card_pan
    bigint amount
    varchar status
    timestamptz paid_at
  }
```

(The `ship_*` snapshot also includes recipient mobile, address line, plaque and unit.)

Order status lifecycle:

```mermaid
stateDiagram-v2
  [*] --> PENDING_PAYMENT : checkout (stock reserved)
  PENDING_PAYMENT --> PAID : payment verified
  PENDING_PAYMENT --> CANCELLED : customer, admin, or 30 min without payment
  PAID --> SHIPPED : admin ships
  SHIPPED --> DELIVERED : admin confirms delivery
  PAID --> REFUNDED : admin records a refund
  SHIPPED --> REFUNDED : admin records a refund
  DELIVERED --> REFUNDED : admin records a refund
  DELIVERED --> [*]
  CANCELLED --> [*]
  REFUNDED --> [*]
```

- Orders are financial records: users with orders cannot be deleted (`ON DELETE RESTRICT`).
- The database checks `total = items_total + shipping_fee` and
  `line_total = unit_price * quantity`.
- Payments keep one row per attempt, following Zarinpal's flow: request an `authority`, redirect
  the customer, verify, store `ref_id`. Unique `authority` and `ref_id` make callback handling
  idempotent.
- Checkout runs in one transaction: check stock, decrement it (reserving it), create the order
  and items, empty the cart. Stock goes back when an order that has not shipped is cancelled or
  refunded. Unpaid orders are cancelled after the payment timeout (30 minutes), unless a payment
  attempt started in the last 15 minutes is still open.
- Every status change locks the order row first (`SELECT ... FOR UPDATE`), so the payment
  callback, the expiry job and admin actions never interleave. The callback verifies with the
  gateway while holding that lock, so a payment is never verified twice.

## Layer 5: Engagement

```mermaid
erDiagram
  USERS ||--o{ REVIEWS : writes
  PRODUCTS ||--o{ REVIEWS : receives
  REVIEWS {
    bigint id PK
    bigint user_id FK
    bigint product_id FK
    int rating "1 to 5"
    varchar title
    text comment
    boolean recommended
    boolean verified_purchase
    varchar status "PENDING, APPROVED, REJECTED"
  }
```

- One review per user per product (`UNIQUE (user_id, product_id)`); only APPROVED reviews are
  shown.
- `verified_purchase` is set by the service when the user has a DELIVERED order with that product.

## Delete behaviour

| Parent → child | On parent delete |
| --- | --- |
| users → addresses, carts, reviews, refresh_tokens | Cascade |
| users → orders | Restrict |
| provinces → addresses | Restrict |
| categories → categories, products | Restrict |
| brands → products | Set null |
| products → specs, variants, images, reviews | Cascade (blocked in practice once a variant is sold) |
| product_variants → product_images | Set null |
| product_variants → cart_items | Cascade |
| product_variants → order_items | Restrict |
| carts → cart_items, orders → order_items | Cascade |
| orders → payments | Restrict |

## Planned extensions

Product Q&A, wishlists, coupons, and Persian full-text search (e.g. `pg_trgm` indexes; today's
search is `ILIKE` per word, which is fine for a small catalog).
